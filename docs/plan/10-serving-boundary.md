# Serving boundary implementation and live rollout

Approved scope is recorded in [AGENTS.md](../../AGENTS.md), the [November 21 serving decision](../requirements/09-recorded-decisions.md#serving-boundary--november-21-2026), and [AC-19 through AC-23 and AC-44 through AC-46](../requirements/06-acceptance-and-coverage.md). This is the plan for the next implementation turn. No rollout has started.

## 1. Establish the baseline

- Read the active checkout, release tags, and the current Linux leech branch. Keep the superseded Strata-specific experiment separate. The general fix applies at Mango's admission boundary and to all provider adapters.
- Confirm the enrolled fleet and each node's effective version, contribution state, platform, ingress paths, provider ownership, aliases, live slots, and updates. Preserve local preferences and deployment identities. Capture sparse metadata from a reproduction if the old build is still in use. The original failure was GamingDesktop loading `flash-next` and Mango rejecting before Strata inference over an estimated memory reserve, after which Luna completed the request.
- Exercise the current residency behavior before changing it. Preserve the existing wait, unload, settle, and reload paths where they already match the decision. Specifically check whether an endpoint-wide busy or operation guard prevents loading YOLO B alongside active YOLO A on a provider that supports it.

## 2. Implement the boundary

1. **Forward ordinary work to the host program.** Follow `PeerScheduling` through catalog observation, candidate selection, `ProviderCatalog.Placement` and `TryStart`, and `InferenceRequest` forwarding. Remove workload and resource-budget eligibility gates, missing context as a substitute for incompatibility, speculative prompt/output fit vetoes, and sole-model load or execution RAM/VRAM/commit checks. Keep public identifiers, true provider capabilities, key scopes, valid protocol, explicit contribution, priority, live slots and benchmark occupancy, and verified settlement. Report provider refusals as provider refusals. Keep leases needed for cancellation and attempt ownership.
2. **Keep user-activity leech independent.** In `ResourceProtection`, retain sustained attributed external CPU/GPU detection, managed release, quiet cooldown, and ingress service. Exclude managed inference and benchmarks from the trigger. Apply the leech transition to YOLO deployments too. Removing memory-pressure withdrawal must also remove pressure-only holds from migrated state without losing manual leech, pending process release, or unfinished attempt fencing. Keep memory telemetry available for observation and checked loads.
3. **Check only an additional non-YOLO load.** Reuse resource measurements, deployment fingerprints, owner overrides, and the existing serialized load or reservation path. Accept comparable native or benchmark RAM and per-device VRAM evidence. An override takes precedence for the value supplied. Check actual simultaneous demands and transient load peaks against headroom, counting resident allocations and outstanding load commitments once. Treat unified memory as a single pool. When fit is unknown or insufficient, use the alternate-first path, then an authorized serial swap if needed and possible. Avoid estimating fit from utilization, generic bytes-per-token formulas, or unrelated hardware. Keep the check atomic through load and settlement.
4. **Make alternate-first swaps work in both directions.** Reuse the queue and existing provider lifecycle methods. Try an eligible alternate before holding the request on a busy or disruptive placement. Keep the original deadline and priority. With no alternate, wait for conflicting running work to finish, reserve the next start under the queue rules, unload the necessary residents, verify release, then load and serve only the requested model. If any required resident is YOLO, unload its whole resident YOLO group after the last group request completes. Use the same sequence returning from non-YOLO to YOLO. Keep later conflicting work from extending an admitted switch indefinitely. Respect explicit lifecycle authority, provider limits, and partial or uncertain release. When the provider supports an additional YOLO load while other YOLO requests run, submit that load without a Mango fit check or a wait for those requests. Every YOLO model reloads individually when requested.
5. **Use live occupancy to spread aliases.** Rank an eligible idle alternate ahead of waiting behind a busy worker for independent requests, even with different reported context sizes or unknown fit estimates. Keep native compatibility signals and bounded affinity for actual continuations. If an attempted host becomes busy or declines before output, use the existing safe retry and ownership rules. Refresh stale placement evidence when needed. Avoid duplicating prompts across candidates.
6. **Align controls and compatibility.** Keep YOLO, activity/cooldown, checked fit evidence and overrides, active benchmark scheduling, and diagnostics. Remove serving prerequisites for complete profiles and UI fields that only enforced ordinary execution budgets. Migrate settings without changing aliases, keys, update preferences, or host authority. Keep peers compatible with the current protocol window where possible. Test mixed-version observations and rollout ordering before deciding whether a compatibility change is needed.

## 3. Verify before release

Extend the existing fixtures and run the focused resource, telemetry, YOLO, provider, cold-route, shared-alias, scheduling, and settlement checks, then run the full Release suite. Verify the Windows package with the release qualification entry point. Produce and test the Linux package and updater path used by the enrolled leech. Use the SDK in `global.json`.

| Case | Evidence required |
| --- | --- |
| Ordinary load and inference | A provider fixture receives a cold sole-model load and valid inference despite tight RAM/VRAM, missing telemetry and profiles, and a legacy allocation fault. Stale instance, auth, invalid input, provider error, and incomplete response still produce their proper outcomes. |
| Checked co-residency | Matching data allows a second non-YOLO load. RAM shortage, a single discrete device shortage, missing evidence, and simultaneous requests exercise reroute or safe serial loading. An owner override changes placement without a hidden generic floor. Independently verify unified-memory accounting. |
| YOLO while busy | On a capable provider, YOLO A keeps generating while B loads and runs. A true provider refusal is surfaced or rerouted safely. |
| Swaps in both directions | With an eligible alternate, the original residents stay put. With the alternate unavailable, allow active A and B to complete, evict the entire YOLO group, verify release, and load only non-YOLO C. Then wait for active C to finish, evict C, and load only A. Request B while A generates and confirm both are active. Include old queued work, a later conflicting arrival, missing unload permission, and an ambiguous release. |
| Activity and benchmarks | Inference and benchmarks alone leave contribution active. A bounded external workload triggers leech including YOLO, keeps ingress usable, and renews the quiet window while activity continues. An active benchmark can occupy its slot and yields or settles correctly. Missing profiles and memory pressure alone cannot withdraw a node. |
| Routing and cancellation | Two long independent `flash-next` streams overlap on different peer fixtures even if one has a smaller advertised context or incomplete benchmarks. Preserve priority, affinity for actual continuations, one execution owner, original deadline, and no automatic replay after output. |

## 5. Qualify on the live network

1. After staging the Windows workers, submit two independent, bounded long streaming requests to `flash-next`. Include a staggered pair with the first visibly generating when the second arrives. Use synthetic requests comparable to the earlier long workloads, including tool declarations if the deployed providers support them. Confirm both complete against different native workers and their generation intervals overlap. Repeat through `star-server-mini` after updating it, using the authenticated client ingress path. Use route attempt IDs, serving node, native usage and timing, and provider status as evidence.
2. Reproduce cold and warm GamingDesktop behavior with the eligible alternate occupied or unavailable for the test. Confirm that Strata receives the valid request once loaded and that Mango does not demand extra execution VRAM. If Strata refuses, record its own error and prove safe reroute separately. Verify that a foreground request arriving during an opportunistic benchmark can progress once the benchmark settles and cleanup releases any runtime it owns.
3. Use small models on a real provider already capable of multiple resident models for the checked and YOLO cases. Verify actual native start/finish, group unload after the last running YOLO request, only the requested model loaded after each switch, and the second YOLO load overlapping the first model's generation. Test each direction with an alternate and with no alternate. Use scoped test aliases or reversible owner settings to isolate these checks. Exercise an insufficient-fit case through checked limits without stressing the production host to allocation failure.
4. Use a bounded external workload on a suitable contributor to verify whole-node cooldown, continuing ingress, and resumption on a quiet host. Check that Mango's own inference and benchmarks do not trigger it. Confirm native model names or configured aliases are returned in model lists, streamed responses, and embeddings, including direct LM Studio access where applicable.
5. Verify the Applebot inference path from its project through the existing private Docker relay. Confirm authenticated chat and the expected embedding model and vector length. Verify a real application request uses its primary provider from Mango and application telemetry. Keep the relay inference-only and leave existing keys, privacy boundaries, and operational settings in place. Use actual request telemetry to distinguish fallback from the model's conversational claims.
6. Record the release digest and observed version for every enrolled peer, the attempt IDs and overlap intervals for concurrent requests, the native lifecycle evidence for swaps, and any pending hardware cases. Use sparse logs and keep credentials and private payloads out of the record. Restore temporary test settings and report any hardware still pending. Fleet rollout is complete only once every enrolled peer's state and relevant live path have been verified.
