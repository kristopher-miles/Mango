Product and connectivity

Q01

Platforms and scale

Which platforms and operating envelope should the first qualified release promise?

Recommended answer

Windows, Apple-silicon macOS, and Linux for the Mango client and GUI, with provider/telemetry support qualified separately. Start with 1–20 nodes and 100 deployments. Use the proposed idle targets of under 1 percent of one CPU core, 150 MiB background-service memory, and 1 KiB/s average control traffic per node as targets to validate, not promises already established. Report the total footprint including Tailscale and the open GUI separately.

This makes “lightweight” testable without claiming unlimited scale. A narrower platform set would reduce initial qualification work. Affects PRODUCT-01, NFR-01–04.

Q02

Tailscale installation

Should Mango require the existing Tailscale client or embed Tailscale?

Recommended answer

require an installed, authenticated client initially and make setup checks clear in the GUI. Retain embedding as a packaging option to assess after the stack is chosen. tsnet is real, but it creates another authenticated device identity and ties the direct embedding path to Go.

Embedding could improve first-run convenience, but its lifecycle, device permissions, and footprint need qualification. Neither option removes user authentication. Affects NET-03, PRODUCT-02.

Q03

Public HTTPS

Which public exposure path should Mango support, and should it ever enable exposure automatically?

Recommended answer

exposure is off until the local owner enables it. Support a general HTTPS reverse proxy, with Tailscale Funnel as an optional guided path when its restrictions fit. Creating an inference key never enables public serving by itself. Publish only the inference surface.

A Funnel-only choice is simpler but imposes its domain, port, platform, and bandwidth constraints. Affects PUBLIC-01–04.

Authority and consistency

Q04

Administrative access from peers

Does joining the network grant unrestricted settings administration, or should sensitive changes require a fresh master-password unlock?

Recommended answer

all enrolled nodes may use resources and view shared state; any node may administer the network after a short local master unlock. Require it for key management, enrollment, shared configuration, retention clearing, and update policy. Keep resource protection and process-control permission local to the host regardless of unlock elsewhere.

This retains peer equality while limiting what an unattended unlocked GUI or ordinary peer credential can change. Public inference keys never become administrator credentials. Affects AUTH-07, UI setting boundaries.

Q05

Shared changes during partitions

Should the network prioritize safe global ordering or accept administrative changes on isolated peers?

Recommended answer

serialize membership, ordered join IDs, authority changes, and shared configuration commits through a temporary coordinator with fenced authority and a majority of enrolled voting peers. Any node can originate the change. Inference and immediate local resource withdrawal continue without a majority. Model observations remain host-owned.

The cost is significant: in a two-node network, both must be online for globally committed writes. An alternative is eventual merging with explicit conflicts and weaker ordering guarantees. Do not hide this tradeoff behind “decentralized.” Affects NET-05, SYNC-03–05, LOG-12. Also determines whether Q06/Q07 can promise authoritative freshness.

Q06

Password recovery and compromise

What should recovery preserve, and must the printed recovery record rebuild authority after all peer state is lost?

Recommended answer

support both password replacement on a surviving network and authority recovery from an adequate offline recovery record. Ordinary recovery rotates the master/recovery authority and invalidates administrative sessions while preserving enrolled nodes and existing inference keys. Offer a separate compromise-recovery action that revokes peers/keys and requires reenrollment. Neither path recovers deleted logs or provider secrets automatically.

A full compromise recovery is more disruptive but appropriate when secrets were stolen. Lost-all-peers recovery needs more than a short password-reset code and cannot reconstruct a lost catalog or key registry without a replica/backup. Forced recovery without the old quorum starts a new network generation and prevents old partitions from regaining write authority automatically. Affects AUTH-04–06.

Q07

Revocation while peers are offline

How much stale authorization is acceptable, and what happens to work already using a revoked key?

Recommended answer

public ingress may accept only authoritative revocation state no older than 60 seconds, refreshed on demand during traffic; if freshness cannot be established, fail closed for new public work. Cancel queued and active requests as soon as their serving node learns the revocation, and refresh authority for long-running public work under the same bound. Trusted private peer inference may continue while partitioned, but known revocations always win.

This introduces bounded security-related network checks. Immediate worldwide revocation with indefinite offline availability is not achievable. A longer window improves availability but increases exposure. Affects KEY-07/09–11.

Q08

Key policy and limits

Should keys have a fixed priority, what additional scopes should exist, and which initial limits are appropriate?

Recommended answer

one fixed low/normal/high priority per key, default normal; permitted task types plus optional alias restrictions; unique display name; 90-day default expiry with an explicit non-expiring choice for private integrations. Begin with the unknown-key lookup limits in KEY-07 and finite configurable per-key rate, concurrency, and payload limits. Label these limits as per-ingress unless a later network-wide quota design is explicitly required.

Trusted peer-originated work carries its node identity and defaults to normal priority; elevation requires administrative policy. Forwarding public traffic never removes its original restrictions. Do not promise a strict global rate quota from independent node counters. The exact workload-dependent valid-key limits can be tuned during qualification. Affects KEY-01–08, QUEUE-08.

Providers and model contracts

Q09

Authority over existing inference servers

May Mango shut down an existing server it did not start, and who grants that authority?

Recommended answer

the local owner explicitly places each provider in managed or attached mode. Managed mode grants a defined load/unload/stop path and is required for a promise of automatic resource reclamation. Attached mode permits inference but clearly states when Mango cannot release the provider's resources. Do not stop unrelated processes or the provider GUI merely because names match.

Automatic downloads, provider installation, training, and weight distribution remain outside the initial scope. This qualifies the original blanket shutdown behavior where Mango lacks control. Affects PROVIDER-03–07, RESOURCE-06/07, SCOPE-09.

Q10

Initial API coverage

Which exact provider profiles and client protocols must the first complete release support?

Recommended answer

qualify Unsloth Studio/API and unsloth run, LM Studio native management plus inference, and supported llama-server single-model/router profiles. Cover model listing, chat completions with streaming and client-executed tool calls, embeddings, image generation, transcription, speech generation, and a specifically named structured-decision contract. Use the documented System One style as the decision-contract candidate to validate. Support each operation where the installed backend/model provides it.

Treat full Responses, Anthropic Messages, video, realtime duplex audio, and general persistent job/file workflows as separately approved extensions. This keeps image/audio/decisions in scope without promising every vendor API. Affects PROVIDER-07, API-01–04.

Q11

Provider tools and code execution

May an inference request cause a provider to run code, browse, or invoke tools on a contributing host?

Recommended answer

no provider-side execution by default. Preserve tool calls returned to and executed by the client. Explicitly disable backend-hosted tools when forwarding into a localhost provider, because the backend may otherwise trust the request as local.

Allowing host execution would need separate local permission, key scope, isolation, and failure semantics. It should not be smuggled into ordinary text inference. Affects API-05.

Q12

Alias compatibility beyond modalities

Should alias validation remain strictly modality-only, or add technical checks for outputs that must be interchangeable?

Recommended answer

retain exact matching of input/output modality sets and never validate quality claims. Also require compatible embedding dimensions/encoding and warn that equal dimensions do not establish a common vector space. Pin an embedding collection to a deployment or owner-declared compatible family. Preserve deployment-specific feature and context checks for every request.

The embedding rule is an explicit extension to your validation limit; it prevents silent corruption without judging model intelligence. If rejected, record that callers assume all embedding compatibility risk. Affects MODEL-02–06.

Q13

Benchmark permission and context verification

Should full-context tests run automatically even when expensive, and how should unreported limits be handled?

Recommended answer

get local permission for the benchmark suite, show its expected size, and make it cancelable. Measure short, half, and full usable context with reserved output and synthetic input, subject to a time/resource budget. Mark skipped or failed tests incomplete and schedule conservatively. Require a configured or verified served limit when the provider cannot report one; never silently substitute the model's theoretical maximum.

This retains your full-context measurement requirement while allowing an enormous or unsafe test to be deferred honestly. Affects CONTEXT-04, BENCH-01–06.

Q14

Memory safety defaults

Which default safety margins and overlap policy should apply before a node is fully characterized?

Recommended answer

reserve the greater of 15 percent or 2 GiB host/unified memory and the greater of 10 percent or 1 GiB per discrete GPU, adjustable locally. Use conservative non-overlap for unmeasured combinations. Require context/concurrency peak evidence and a live admission check before overlapping models.

These are starting values to calibrate, not universal guarantees. A provider can still allocate unexpectedly, and another local program can race for memory. Affects MEMORY-01–06, BENCH-06.

Q15

Activity detection and cooldown

What should trigger withdrawal, when should contribution resume, and what happens when process attribution is unavailable?

Recommended answer

local CPU/GPU/memory observation with up to 2-second samples, a 10-second sustained external-load trigger, immediate withdrawal for severe memory pressure, and five continuous quiet minutes before resuming. Renew the quiet period on new load. Manual leech mode persists. Treat missing attribution as a visible limitation and require a conservative local choice before automatic contribution.

The provisional external-load threshold needs hardware calibration; detecting “any input” should not automatically mean heavy load. Affects RESOURCE-02–07.

Scheduling and client behavior

Q16

Scope of queue purging

Should a higher-priority arrival clear every lower-priority queued request on that node, or only requests competing for the same resources?

Recommended answer

clear only conflicting lower-priority work. A job using an independent GPU or genuinely nonconflicting CPU capacity should continue or be admitted if it cannot delay the higher-priority reservation.

This is a deliberate narrowing of “all lower priority requests in the queue.” Literal node-wide purging is simpler to describe but can reject useful work without freeing the needed resource. Affects QUEUE-05/06.

Q17

Scarcity versus priority

Does a low-priority request with one possible destination outrank a high-priority request with several destinations?

Recommended answer

no. Keep safety, authorization, and the explicit priority admission/rejection rules hard. Route flexible work elsewhere to maximize service, then use fewer eligible destinations to break contention among equal-priority requests, followed by FIFO.

Your “always lower priority” scarcity sentence and the later priority hierarchy conflict in this case. If scarcity should override key priority, say so explicitly; the queue rejection rules will need corresponding changes. Affects PRODUCT-05, ROUTE-02/03.

Q18

Active work and starvation

Should ordinary priority changes abort running inference, and how should a waiting large model avoid endless postponement by small requests?

Recommended answer

let active requests finish during ordinary scheduling. Higher priority displaces queued work, while local activity, explicit cancellation, revocation, and faults can abort active work. Reserve an admitted scarce request's next feasible start and stop backfilling jobs that would delay it. Permit safe cancellation of loading work before inference begins when justified.

Retain strict priority rather than silently aging low-priority work upward; under sustained high load, low-priority work may starve or be rejected. Affects QUEUE-07, ROUTE-06, MOVE-01.

Q19

Client identity and affinity

How should Mango identify a continuing conversation, how long should it remember it, and how long may cache reuse delay a request?

Recommended answer

use an explicit session identifier scoped to authenticated key identity, with bounded in-memory prefix comparison/digests as fallback. Expire ordinary affinity five minutes after completion. Keep unrelated work under the same key independent. Wait for a cached instance only when estimated benefit beats another placement and the client deadline permits it.

Never equate source IP or API key with one conversation. Do not persist prompt bodies solely for affinity. Affects AFFINITY-01–05; the future best five-minute rule is already confirmed.

Q20

Retries and partial results

May Mango automatically restart a request elsewhere after execution starts or the client has received output?

Recommended answer

automatic retry only when no output has been committed and the operation is known to be replay-safe. After partial output or possible side effects, return an interruption with request/attempt identity. Require an explicit client retry rather than concatenating a second generation into the original stream.

Reassigning queued work remains allowed after ownership transfer. Live cache or backend-held conversation migration is not promised. Affects QUEUE-03, MOVE-03–05.

Q21

Queue limits and overload

What bounds and failure contract should apply when work cannot start promptly?

Recommended answer

start with 64 waiting requests per serving node, 8 per key per node, and 120 seconds of queue residence for ordinary text/embedding work, plus finite byte limits and separate media deadlines. Use 429 for a client's rate/quota limit and 503 for unavailable inference capacity, with clear reason codes and useful retry hints. Bound rerouting attempts by distinct candidates and the request deadline.

Long-running media may need larger explicit deadlines; no request should wait indefinitely. These counts are tuning defaults, not a substitute for byte/resource limits. Affects QUEUE-08–10, ROUTE-07.

Q22

Low traffic and failure detection

Is a small amount of bounded liveness and local inventory checking acceptable when event APIs are insufficient?

Recommended answer

yes. Prefer events, cached state, demand-driven checks, and daily reconciliation. Allow a slow local provider fallback, initially no more often than once a minute while enabled, and cheap bounded checks for active routing, security freshness, and temporary coordination. Do not scan every peer per request or fetch unchanged full catalogs repeatedly.

Without these exceptions, an externally changed server or dead peer can remain stale until the next request or daily refresh. Event API support also differs by provider/version. Affects SYNC-06, NFR-03, NET-03, KEY-09.

Interface and operations

Q23

GUI form and headless machines

Should the product support headless machines, and what form should the GUI take?

Recommended answer

a desktop/tray experience backed by a service, with an authenticated local browser GUI usable for headless deployments. Keep the layout responsive and accessible, and allow shared model administration from any enrolled node. Resource-protection settings still require local host access.

Do not add a native mobile app or publicly exposed admin console to the initial scope. The exact UI technology belongs in the later plan. Affects UI-01–08.

Q24

Logging contents and privacy

Should sparse logging be the default, what does verbose “exactly” include, and does tts mean tokens per second?

Recommended answer

default sparse; interpret tts as tokens per second and name it explicitly. Verbose records exact inference request bodies with explicit credential exclusions; do not retain response bodies by default. Off creates no persistent request logs, including a hidden per-request audit trail. Required revocation/configuration/update state remains operational state, not logging.

If full responses are wanted, add them explicitly with retention and storage implications. Prompt text can contain secrets even after transport credentials are removed. Affects LOG-01–09.

Q25

Daily logs and deletion

Which day boundary, retention, completeness, and clearing behavior should apply across intermittently connected nodes?

Recommended answer

one network timezone selected at setup, defaulting to the first node's timezone; UTC timestamps; seven days of raw records and thirty days of aggregate metadata, within a 1 GiB per-node total cap. The lowest eligible join ID collects; offline peers produce a visibly incomplete aggregate, with late merge and deduplication. Network clear remains pending for offline peers and applies a deletion generation before their old data can rejoin.

This does not guarantee archival redundancy or deletion of user exports. Affects LOG-10–18.

Q26

Coordinated updates

Does “at the same time” mean coordinated queueing or simultaneous restart, and how much can a node update automatically?

Recommended answer

coordinate one verified release intent and queueing window, then perform rolling installation with bounded draining, local deferral, health verification, and rollback when the data format permits it. Warn before proceeding when a peer cannot verify eligibility; require the initiating user's explicit compatibility-risk override. Never override an invalid signature.

Coordinate Mango only. Leave Tailscale, drivers, providers, and model weights under their own update controls. Simultaneous restarts would deliberately remove all capacity and complicate recovery. Affects UPDATE-01–04/08–11.

Q27

Mixed-version compatibility

How much backward compatibility should releases promise without requiring all nodes to match?

Recommended answer

publish a feature/protocol compatibility matrix and initially support the current and previous compatible protocol generation. Negotiate shared features regardless of application version numbers. Keep diagnostic connectivity where possible, but reject specifically incompatible operations safely.

“Do not lock out different versions automatically” cannot mean decoding unknown or unsafe protocols. Affects UPDATE-05–07.

Best-model interpretation and preparation

Are the proposed capability ratings, capacity tiers, classifier fallback, and reserved name appropriate for the future feature?

Recommended answer

shared labels and deployment-specific 0–5 ratings with unrated distinct from zero; one primary task label; first choose the strongest eligible open-capacity deployment, including safe immediate cold loading; then prefer eligible loaded deployments that can legally queue; then the best other legal queue. # Mango product scope

Mango shares inference capacity across the user's machines without requiring a particular inference engine or a common local network. It routes whole requests to existing servers, protects each machine's local workload, and exposes a consistent catalog and access policy.

## Product requirements

**PRODUCT-01 — C.** Support any number of installed peers as a product concept. Each peer can access inference resources across the enrolled Mango network. The supported and tested scale must be stated explicitly; the product cannot promise unlimited capacity or cost-free replication.

**PRODUCT-02 — C.** Make Tailscale the network foundation from the beginning. Machines may be on different physical networks. Users authenticate with Tailscale and separately enroll into the intended Mango network.

**PRODUCT-03 — C.** Make nodes lightweight, favor pushed changes and demand-driven requests, and avoid constant network polling. A contributor may become a leech manually or automatically when other activity needs its resources.

**PRODUCT-04 — C.** Connect to Unsloth, LM Studio, and llama.cpp out of the gate. Keep additional providers and inference protocols extensible. Text, image, audio, embeddings, and structured decisions belong in the product scope; exact first-release contracts are pending Q10.

**PRODUCT-05 — C.** Prefer serving as many requests as possible with the available nodes, then request priority, then first in first out. Preserve the explicit low-priority rejection and queue eviction rules. Resolve their interaction with model scarcity in Q16–Q18 rather than silently replacing them with a conventional scheduler.

**PRODUCT-06 — C.** Provide a responsive GUI on every machine. It can configure shared model endpoints, aliases, capabilities, and ratings across the network. Resource protection settings remain local to the machine they protect.

**PRODUCT-07 — C.** Support scoped, individually revocable inference keys; optional internet HTTPS serving; coordinated software updates; configurable logging; and daily or on-demand network log aggregation.

**PRODUCT-08 — F.** Reserve the future `best` routing feature described in its own document. Its model-selection logic is not part of the initial implementation.

## Terms

| Term | Meaning |
| --- | --- |
| Mango network | An application trust group with its own identity and credentials; it is not automatically the whole tailnet. |
| Peer or node | One enrolled Mango installation, identified independently of hostname and IP address. |
| Join ID | A persistent, ordered enrollment identifier. Its order determines the oldest eligible log collector. It is not a routing priority. |
| Contributor | A node allowed to accept inference work on its local resources. |
| Leech | A node that may submit and route requests but contributes no inference compute. |
| Ingress node | The Mango node a client connects to. It retains the client connection and routes work. |
| Serving node | The node that admits a request to its execution queue and controls the local provider. |
| Provider | An existing inference server and its management interface, such as LM Studio. |
| Model artifact | A particular set of weights, quantization, tokenizer, and associated files. |
| Model instance | A model loaded with a particular context, device allocation, runtime, and concurrency configuration. |
| Model alias | The client-visible name that may group compatible deployments, even of different quality or quantization. |
| Capability | A user-defined task label such as coding, writing, or classification. This differs from a technical feature such as image input or tool-call output. |
| Rating | A user assessment of a deployment's strength at one capability; it is not a verified benchmark score. |
| Modality | A type of input or output, such as text, image, audio, or embedding vectors. |
| Eligible destination | A contributor satisfying the request's authorization, protocol, modalities, context, and resource requirements. |
| Open capacity | Capacity available to admit execution now within safety limits, including the chosen policy for loading an unloaded model. It does not mean merely that a model is installed. |
| Affinity | A preference to return related requests to the same provider instance to reuse its cache or state. |
| Queue | Work admitted to wait at a serving node. An ingress forwarding record is not a second execution queue. |

## Settled interpretations

**SCOPE-01 — I.** The network distributes independent requests. It does not combine GPU memory across machines, split one model across the WAN, or transfer live model execution between unlike runtimes. A backend may itself use multiple local GPUs; Mango treats that as one serving deployment.

**SCOPE-02 — I.** Peer equality does not require a permanently running central inference server. The first node initializes the network; it need not stay alive to route inference. A temporary coordination role for shared metadata or logs does not grant ownership of other nodes' local controls.

**SCOPE-03 — I.** Tailnet membership alone does not grant Mango membership. Conversely, Mango enrollment does not bypass Tailscale policy or expose unrelated services on another machine.

**SCOPE-04 — I.** A leech still receives client requests, control messages, and catalog updates. It must remain usable as an ingress and as a GUI. Shutting down inference does not mean shutting down Mango or Tailscale.

**SCOPE-05 — I.** Model availability has several states: installed but not loaded; loading; loaded and available; loaded and busy; unloading; disabled; unreachable; and failed. A stale advertisement is a routing hint, not permission to exceed the serving node's current resources.

**SCOPE-06 — I.** Aliases do not certify model quality, identical tokenization, identical embeddings, or shared caches. GGUF and MLX deployments can share a name while retaining separate measurements and provider identities.

**SCOPE-07 — I.** Resource-driven relocation usually changes where queued work or the next request runs. Completing an active request before unloading, as in the supplied example, is distinct from aborting it because local user activity takes precedence.

**SCOPE-08 — I.** The inference network is private infrastructure controlled by trusted owners. Scoped public clients are outside that administrative trust group. Protecting against a fully compromised peer requires removing it and rotating affected authority; a peer that serves a request necessarily sees that request's contents.

## Scope boundaries

**SCOPE-09 — P, Q09/Q10.** Integrate installed providers and models first. Do not add a model marketplace, training, automatic weight downloads, weight distribution, billing, or a general remote shell. Starting or stopping an explicitly managed provider is within scope. Future protocol adapters must not turn ordinary inference access into arbitrary host administration.

**SCOPE-10 — I.** Publishing a public inference endpoint is optional and separate from creating a key. A key does not create a DNS name, issue a TLS certificate, open a firewall, or configure a public proxy.

**SCOPE-11 — I.** Requirements may later be implemented in stages. No stage order, sprint breakdown, technology selection, or implementation estimate is approved by this draft.

## Proposed measurable targets

**NFR-01 — P, Q01.** Initially qualify Windows, macOS on Apple silicon, and Linux for the Mango client and GUI; qualify provider and telemetry combinations individually. Test 1–20 peers and 100 advertised deployments. Larger networks may work but are outside the first measured envelope.

**NFR-02 — P, Q01.** With 20 peers, no inference, GUI closed, and an unchanged catalog: target less than 1 percent of one CPU core averaged over 15 minutes and at most 150 MiB resident memory for Mango's background service. Measure the GUI, Tailscale, providers, and optional embedded networking separately and also report the total installed idle footprint. Do not hide a bundled dependency's cost.

**NFR-03 — P, Q01/Q22.** Target no recurring full catalog fetches other than the daily reconciliation. Target at most 1 KiB/s average idle Mango control traffic per node at the stated scale, excluding inference and one-time reconciliation bursts. Instrument message counts, bytes, wakeups, reconnects, and CPU so these claims can be checked.

**NFR-04 — P, Q01.** Target local GUI feedback within 200 ms for ordinary actions; show progress for network-dependent operations. Target less than 25 ms p95 Mango admission and routing overhead on a local healthy path, excluding authorization refresh, provider work, model loading, queue time, and WAN transit. Report these exclusions with measurements.

**NFR-05 — I.** Bound queues, connection buffers, cached request state, pending synchronization, unknown-key lookups, and logs. Saturation must produce a defined failure rather than unbounded RAM use or silent data loss.

**NFR-06 — I.** Timing claims must be measured on named hardware and scenarios. Reachability, revocation, and metadata freshness guarantees must name their behavior under sleep, packet loss, partitions, and clock changes.

# Mango network and security requirements

Tailscale supplies private connectivity. Mango supplies enrollment, resource access, model metadata, and inference-key authority. These are separate trust boundaries, including when all devices belong to the same person.

## Connectivity and joining

**NET-01 — C.** A newly started node actively discovers reachable Mango peers through its tailnet and negotiates enrollment. It prompts for the master password when joining an existing network. An already enrolled node reconnects with its own identity rather than asking for the master password after every boot.

**NET-02 — I.** A peer must retain a small inbound service for enrollment handshakes, authenticated control messages, and inference traffic. Active discovery removes repeated scans by existing peers; it cannot eliminate listeners needed to receive requests. The requirement is low idle cost, not absence of listening sockets.

**NET-03 — P, Q02/Q22.** Use the installed and authenticated Tailscale client initially. Read the known peer set, try remembered Mango peers first, then probe only candidate tailnet addresses on the Mango service port with bounded concurrency and a deadline. Do not scan the tailnet address range or unrelated ports. Support a manual peer address when enumeration or discovery is restricted. A failed search must not silently create a second network.

**NET-04 — I.** Discovery reveals only enough information to identify a candidate network and negotiate supported versions. A node must authenticate the selected network before disclosing secrets or accepting configuration. Joining an unintended network with the same display name must not be possible solely because its response arrived first.

**NET-05 — P, Q05.** Display a network fingerprint or authenticated invitation and verify it during first enrollment. Assign a persistent node identity and ordered join ID through serialized enrollment. Concurrent enrollments must receive unique ordering; restoring a known node retains its identity only when it proves possession of that identity. Copying an installation must not create two live nodes with the same identity.

**NET-06 — C.** Peer traffic must work across the internet without requiring LAN discovery. Handle direct and relayed Tailscale paths. Do not assume low latency, unlimited bandwidth, synchronized uptime, or a permanent public IP.

**NET-07 — I.** Tailscale logout, expired device authorization, policy changes, or unavailable networking must produce a visible diagnosis. Local inference may continue if otherwise authorized and safe. Such a node must not claim successful network replication.

## Index and synchronization

**SYNC-01 — C.** Maintain a local network index. Push updates when model availability changes and reconcile once daily. A node may request an immediate refresh, including on join. Use deltas and revision summaries where possible rather than routinely transferring the complete catalog.

**SYNC-02 — I.** Propagate enrollment and removal, model registration and removal, aliases and capabilities, effective serving limits, contributor state, key issuance and revocation, logging policy, and update coordination. Dynamic queue and capacity hints may travel with admission responses or material state changes; per-token broadcasts are unnecessary.

**SYNC-03 — I.** Replicated changes require an authenticated origin, identity, revision, and replay protection. Duplicate or out-of-order delivery must be harmless. Deletions and revocations must not be undone by an old snapshot. Fetch a full snapshot only when missing history or a revision mismatch requires it.

**SYNC-04 — P, Q05.** Serialize shared configuration and membership changes through a temporary peer coordinator with a fenced leadership term and a majority of enrolled voting peers. Any node can originate an authorized change. Existing inference can continue on reachable nodes when a majority is unavailable, but globally ordered changes cannot be reported as committed. One-node networks work; a two-node network needs both online for such writes. This is a proposal with a real availability cost, not an implied requirement for inference routing.

**SYNC-05 — I.** Model observations and local resource withdrawal remain owned by the reporting machine and take effect there immediately, including without a majority. Shared requested configuration and locally observed operational state must be distinguishable. A remote edit cannot overwrite a newer local safety state.

**SYNC-06 — P, Q22.** Use available transport and provider events, request-triggered checks, reconnect synchronization, and jittered daily reconciliation. Permit inexpensive bounded liveness checks when necessary for active routes, coordination, or revocation freshness. Permit a slow local provider inventory fallback if no event interface exists. Their limits must be visible and measured; there is no full-network polling loop.

**SYNC-07 — I.** Failed updates enter a bounded retry path with backoff. Mark a peer's state stale when freshness is unknown. On reconnection, reconcile revocations and deletion markers before advertising that stale local information is current. Do not broadcast a separate full network snapshot in response to each peer's daily refresh.

## Network authority and recovery

**AUTH-01 — C.** The first peer establishes a master password and a separate recovery key. The recovery key can replace a lost master password. Show an exportable, printable recovery record and explain that it should be stored outside the network. Never print or upload it automatically.

**AUTH-02 — C.** A user holding the master password can create inference keys from any node. Joining peers requires that authority as well. Ordinary inference must not require sending the master password with every request.

**AUTH-03 — I.** Keep Tailscale credentials, Mango node identities, master/recovery authority, public inference keys, and provider API tokens separate. Never use the master password as an inference bearer token or a transport key. Never store it in plaintext or copy it into logs, URLs, provider requests, or command-line diagnostics.

**AUTH-04 — P, Q04/Q06.** Use the password to unlock administrative authority locally through vetted cryptographic mechanisms; peers ordinarily retain verification material and their own identities. Use a memory-hard password derivation and platform secret storage where available. The actual enrollment and recovery protocol requires security review before implementation; this document does not specify a new cryptographic protocol.

**AUTH-05 — P, Q06.** Recovery advances an authority generation, sets a new master password, rotates the recovery secret, and invalidates administrative sessions and old key-issuing authority. Preserve enrolled node identities and existing inference keys by default, with a distinct compromise-recovery option to revoke and reenroll them. Old backups must not restore superseded authority. Recovery without any surviving trusted state requires the printed record to carry sufficient network recovery material; a password-reset code alone is insufficient.

Forced recovery after loss of the coordination quorum is a disaster-recovery operation into a new network generation. An old partition must not regain write authority automatically. The recovery record restores only the authority it actually contains; it cannot reconstruct the catalog, issued-key registry, logs, or provider secrets without a surviving replica or backup. Reenrollment and key reissuance may therefore be necessary.

**AUTH-06 — I.** Losing both administrative secrets does not erase installed provider models. Existing enrolled peers may still function while their credentials remain usable, but Mango must not offer an unauthenticated takeover path. Creating a replacement network remains possible; imported configuration must not import obsolete authority as valid.

**AUTH-07 — P, Q04.** All enrolled nodes can use resources and view shared state. Require a short administrative unlock for changing shared settings, enrollment, key management, retention deletion, or network update policy. Local-only controls require a session on the target machine. Public inference credentials never grant administrative authority.

## Inference keys

**KEY-01 — C.** Each key has a unique non-private display name for attribution, a stable identifier, allowed inference types, and one of three priority levels. Keys are independently revocable. Creation on any authorized node pushes its verification record to peers.

**KEY-02 — P, Q08.** Give each key one fixed priority: low, normal, or high. Omitted priority is normal. Clients cannot raise priority with a request field. Support optional alias restrictions in addition to task-type scopes, and expiry, rate, concurrent-request, and payload limits. A model name change must not silently broaden an alias-restricted key.

Trusted peer-originated requests carry an authenticated node identity and default to normal priority; elevation requires an administrative policy. A public request forwarded by a peer retains its original key's restrictions and cannot become unrestricted private traffic. Proposed key lifetime is 90 days by default, with an explicit non-expiring choice for private integrations. Limits enforced independently at each ingress must be labeled per-ingress, not represented as strict global quotas.

**KEY-03 — I.** Verify credentials at ingress and enforce their effective authority at the serving node. A forwarded request carries authenticated client/key identity and effective scope and priority; a client-supplied header is not evidence. Do not send Mango credentials to a provider that uses its own credential.

**KEY-04 — I.** Replicate a verification record, not reusable bearer secrets. Show a newly issued secret once; provide replacement and revocation instead of secret recovery. Store token verification material appropriate to high-entropy tokens. A human password's slow verification function must not be run for every random internet token.

**KEY-05 — C.** If a presented key is unknown locally, query other peers sequentially. Stop when a valid authoritative record is found, cache it, and accept only after checking the presented secret, scope, expiry, and revocation state. An individual peer's assertion of validity is insufficient without verifiable authority.

**KEY-06 — I.** Distinguish unknown ID from known ID with an incorrect secret, known revocation, expiry, or insufficient scope. Only the genuinely unknown case triggers discovery. Never let a late valid record override a newer revocation. Peer lookups do not recursively fan out.

**KEY-07 — P, Q07/Q08.** Bound unknown-key recovery by source, ingress-wide budget, concurrent work, number of contacted peers, and total elapsed time. Coalesce identical lookups and maintain a bounded short-lived negative cache. Suggested starting limits are 5 misses/minute/source with burst 5, 30/minute/ingress with burst 10, 2 simultaneous peer lookups, at most 3 peers and 2 seconds per miss, and a 30-second negative cache capped at 1,000 entries. These are tuning proposals. Correctness and known-key inference must survive sustained random IDs and source rotation.

**KEY-08 — I.** Minimize unauthenticated work before parsing or buffering large bodies. Bound uploads, generation limits, connections, queues, compressed expansion, media decoding, and slow clients. Protect outbound media fetches from accessing unintended local or tailnet services. Authentication errors must not reveal the peer inventory or whether a specific secret nearly matched.

**KEY-09 — P, Q07.** Give internet key acceptance a maximum 60-second revocation-state age, refreshed on demand during use. If the node cannot obtain sufficiently current authoritative state, reject new public requests as temporarily unavailable. A cached response from another stale peer cannot extend freshness. Revocation freshness must be tied to committed authority, not merely the time of the last successful peer connection. Trusted private inference may continue under its separately approved policy.

**KEY-10 — I.** No partitioned design can both guarantee immediate global revocation and accept cached authority indefinitely. The UI must show pending propagation and unreachable nodes. A local known revocation takes effect immediately and cannot be overridden by an offline permissive mode.

**KEY-11 — P, Q07.** On revocation, cancel queued requests for that key immediately and cancel active requests when the revocation reaches the serving node. Recheck authority before starting queued work. Authorization freshness for long-running public work must follow the agreed policy rather than being assumed permanent after admission.

## Optional public HTTPS

**PUBLIC-01 — C.** A node can expose authorized inference over public HTTPS when the user enables it. A public client need not join the tailnet or install Mango. Other peers remain privately reachable through the ingress.

**PUBLIC-02 — I.** Public exposure must include valid TLS, request authentication, rate and resource limits, and streaming support. Keep enrollment, provider administration, GUI control, logs, and update commands outside the public inference surface. Do not publish native provider ports as a shortcut around Mango authorization.

**PUBLIC-03 — P, Q03.** Support an existing HTTPS reverse proxy as the general path; offer Tailscale Funnel as a convenience where its domain, port, platform, and bandwidth restrictions fit. Exposing a service remains an explicit local action. The GUI checks the endpoint and explains who can reach it.

**PUBLIC-04 — I.** Trust proxy identity headers only from configured proxies. Apply effective limits even if the external source address is unavailable. A proxy or node changing addresses must not erase the identity used for per-key accounting.

Local browser access also needs authentication and origin/request protections. Being bound to loopback does not make a request from an unrelated web page an authorized local administrator or unrestricted inference client.

# Mango provider and model requirements

Mango routes requests through existing serving infrastructure. Each adapter must describe what its particular server can actually do, including lifecycle control and limits. Sharing an HTTP request format does not make management interfaces interchangeable.

## Provider integration

**PROVIDER-01 — C.** Ship support for Unsloth, LM Studio, and llama.cpp. Additional providers must be addable without changing the scheduler's fundamental rules. Version-specific capabilities must be explicit and testable.

**PROVIDER-02 — I.** An adapter needs operations or explicit unsupported results for: endpoint discovery; authentication; model inventory; loaded instances; effective limits; request execution and streaming; cancellation; loading and unloading; process shutdown; concurrency; health; and resource observations. Not every provider must implement every optional operation, but the GUI and scheduler must not assume it does.

**PROVIDER-03 — P, Q09.** Distinguish managed providers, for which the local owner grants Mango lifecycle authority, from attached providers, for which Mango can only use an existing endpoint. Automatic resource reclamation requires managed authority and a demonstrated release path. An attached server with no unload/stop permission cannot be presented as fully reclaimable.

**PROVIDER-04 — I.** Only the host of a provider executes its local process controls. Identify processes by durable ownership evidence rather than killing all processes with a matching name. Never terminate an unrelated server, provider GUI, training task, or user session to reclaim inference memory. Detect when another controller changes the same server and refresh state.

**PROVIDER-05 — C.** Support endpoint and model configuration from any authorized node's GUI. The owning node validates and applies the change. Changes needing local credentials, new executable access, or expanded shutdown authority must be completed locally, consistent with local resource-control ownership.

**PROVIDER-06 — I.** Discover only configured or recognized local endpoints and user-added endpoints within the approved boundary. Do not run arbitrary URLs, shell commands, or adapter code supplied by an inference client. Store provider tokens on the owning node; shared configuration can show a credential reference and validity state, not the secret.

**PROVIDER-07 — P, Q10.** Qualify Unsloth Studio/API and the `unsloth run` serving profile explicitly, LM Studio's native management API plus inference API, and supported llama-server single-model and router profiles. Record the exact tested versions during implementation rather than declaring every release compatible. An exported Unsloth model served by llama.cpp uses the llama.cpp adapter, not a separate imagined protocol.

## Public inference contracts

**API-01 — C.** Support text, image, audio, structured decisions, and extension to new inference protocols. Embeddings are included because they appear in the scheduling examples. Scope authorization by actual operation and payload, not only by URL or model alias.

**API-02 — P, Q10.** The first compatibility contract should include model listing, chat completions with streaming and client-executed tool calls, embeddings, image generation, audio transcription, speech generation, and one named structured-decision API. Expose only features supported by the chosen deployment. Full Responses, Messages, video, realtime duplex audio, and other contracts are additional explicit coverage decisions, not implied by the phrase OpenAI-compatible.

**API-03 — I.** Preserve supported request parameters, response semantics, structured output, usage accounting, cancellation, and streaming error behavior. Reject an unsupported parameter or endpoint clearly when dropping it would change meaning. Do not pretend that a plain chat response implements a structured-decision protocol.

**API-04 — I.** An adapter declares whether a request is synchronous, streamed, or a job with later result retrieval; what state or file handles it creates; and how cancellation and cleanup work. Provider-local IDs are namespaced and routed back to their owner. A server-held conversation or media handle cannot move to another endpoint unless the required state is transferable.

**API-05 — P, Q11.** Permit model-generated tool calls that the client executes, but disable provider-side code execution, web tools, and MCP execution through Mango by default. A localhost backend may otherwise interpret a proxied request as locally trusted. Any future server-side tool permission must be separate from inference permission and reviewed at the owning node.

## Catalog and aliases

**MODEL-01 — C.** Detect hosted models from their endpoints. Allow the user to assign an alias, capability labels, and a rating for each label. A request using an alias is served by an eligible deployment registered under that alias. Translate the alias to the provider's real identifier at the boundary.

**MODEL-02 — C.** The same alias may represent different quantizations, formats, machines, or even unrelated models of different quality. Validate that deployments sharing it accept the same input modalities and produce the same output modalities. Do not validate honesty of names or ratings, model intelligence, or equivalence of weights.

**MODEL-03 — I.** Retain each deployment's real provider identity, artifact identity where available, loaded-instance identity, actual context limit, technical features, performance, and memory profile. An alias is a grouping label, not a reason to average away hard limits or copy another instance's cache claim.

**MODEL-04 — I.** Separate user task ratings from protocol support. A model rated highly for coding is not thereby proven to support tools, structured JSON, image input, or a particular decision schema. Request-specific features must be matched against the deployment's actual support.

**MODEL-05 — P, Q12/Q28.** Use shared capability labels with deployment-specific integer ratings from 0 to 5; leave unrated distinct from 0. Allow bulk assignment to an alias, with individual overrides. Enforce exact input/output modality sets for shared aliases initially. Broader subset matching is a later policy choice.

**MODEL-06 — P, Q12.** Add a technical output-contract check for embeddings, such as vector dimensions and encoding. This is an explicit extension to the user's modality-only validation rule. Even equal-length embeddings from different models need not share a meaningful vector space: warn about mixing them, and pin an embedding collection to an explicit deployment or owner-declared compatible family. Do not claim to verify semantic equivalence.

**MODEL-07 — I.** Alias changes are revisioned and conflict-checked. An in-flight request retains its resolved deployment and original alias revision. Renaming a model cannot retarget a request midstream. When another node is offline, the UI shows that the change is pending there.

**MODEL-08 — I.** Distinguish discoverable, eligible, and immediately available models in listing and UI. A busy model remains in the catalog; a leech advertises no executable capacity. Inaccessible or unverified context information must not be represented as an unlimited context.

## Served context and input fit

**CONTEXT-01 — C.** Detect the maximum context actually served by a configured instance, not only the model's theoretical training limit. Store theoretical and effective limits separately when both are known. Recheck effective limits after reloads and server configuration changes.

**CONTEXT-02 — I.** For generation, fit the encoded prompt, template and system overhead, tool definitions, multimodal tokens, and reserved output into the effective context. Count with the destination's tokenizer or an authoritative provider count when available. Different deployments under one alias may tokenize the same input differently.

**CONTEXT-03 — I.** Do not fill the entire context with input and then expect output to fit. A full-context benchmark means total input plus its reserved output reaches the usable limit. For embedding and media endpoints, use the appropriate input, batch, duration, resolution, or output limits rather than forcing a text context concept onto them.

**CONTEXT-04 — P, Q13.** If an adapter cannot discover a reliable effective limit, require a user-supplied served limit or a bounded verification procedure before advertising that capacity. Mark its provenance as reported, measured, or user-configured. Token estimates must be conservative, and the serving node retains final validation. Never silently truncate a request to make it fit.

## Benchmarking and resource profiles

**BENCH-01 — C.** Measure short, approximately half-context, and full-served-context requests for text-like models where those tests make sense. Measure system resource use during model loading and execution so the scheduler can judge safe overlap. Do not apply these three prompt lengths indiscriminately to image or audio endpoints.

**BENCH-02 — I.** Record load time, prompt processing time or rate where exposed, time to first token, generation rate, completion time, peak RAM, peak VRAM per device, and configuration. Distinguish cold loading, warm execution, and actual cache reuse. Record unsupported or unobserved metrics as unknown, never zero.

**BENCH-03 — I.** A model's resource cost includes weights, context/KV cache, concurrency, temporary buffers, media encoders or projectors, runtime overhead, and transient load peaks. Record the request size and simultaneous work used for each measurement. One isolated load is insufficient evidence that two models at full context can safely overlap.

**BENCH-04 — P, Q13.** Benchmark with synthetic inputs, opt-in permission, visible progress, cancellation, and a time/resource budget. Run low-cost discovery first, then short, middle, and full tests subject to safety. If a test is skipped or cannot safely finish, retain an explicit incomplete profile and schedule conservatively. Do not silently replace the requested full-context measurement with a tiny sample.

**BENCH-05 — I.** Bind measurements to the artifact, quantization, runtime version, device configuration, context size, cache configuration, concurrency, and relevant adapter version. Material changes invalidate affected confidence. Rebenchmark on relevant changes or user request, not every startup.

**BENCH-06 — P, Q14.** Allow overlapping deployments only with adequate resource evidence and a current admission check. Use conservative non-overlap for unmeasured combinations; permit a local owner to configure a qualified profile. Do not benchmark every possible combination combinatorially, and do not extrapolate a small-context peak into a claim of full-context safety.

## Required catalog information

This is a logical information contract, not a storage schema.

| Record | Required information |
| --- | --- |
| Provider endpoint | Owner node, adapter and version, endpoint, credential reference, management authority, health, available operations |
| Deployment | Provider model ID, alias, artifact/variant where known, modalities, supported tasks/features, limits, installation/load state |

# Mango resources and scheduling requirements

The serving node is the final authority over its resources. Other nodes use its advertisements to select candidates, then request admission. This permits simultaneous clients without treating a replicated catalog as a reservation system.

## Local activity and contributor state

**RESOURCE-01 — C.** Nodes support contributor and leech roles. Switching to leech withdraws local inference availability, aborts active inference, and unloads models or shuts down the inference servers under Mango's control. Requests can still enter the network through that node.

**RESOURCE-02 — C.** Detect high system activity not caused by monitored inference processes. When detected, become a leech until the configured cooldown has elapsed. Activity monitoring, thresholds, enablement, and cooldown are local-only settings. Five minutes is the user's example default, not yet a measured optimum.

**RESOURCE-03 — I.** Track the managed inference process tree, including workers, when attributing load. CPU, GPU, RAM pressure, and device memory matter. Do not assume aggregate GPU utilization minus one process counter is a reliable measure on every operating system. Missing attribution must be visible.

**RESOURCE-04 — P, Q15.** Use native process/resource observations with inexpensive local sampling when events are insufficient. Start with samples at most once every 2 seconds, a 10-second sustained external-load trigger, and a 5-minute continuous quiet period before resuming. Renew the quiet period when high load returns. Severe memory pressure triggers immediate withdrawal. Thresholds require platform calibration; a provisional 50 percent external CPU or GPU threshold must not be treated as universally valid.

**RESOURCE-05 — I.** Manual leech mode persists until the user changes it. An automatic cooldown cannot undo manual withdrawal, maintenance, a resource fault, or disabled contribution. Restarting or resuming the computer must not silently clear those constraints.

**RESOURCE-06 — I.** Withdraw admission before beginning cancellation. Notify ingresses of queued and active request outcomes, cancel provider work, then verify resource release. Publish failure if a server refuses to stop or memory remains allocated. Do not advertise a successful return of resources merely because a stop command was sent.

**RESOURCE-07 — P, Q09/Q15.** Allow a short adapter-specific cancellation deadline, then terminate only an explicitly managed process if necessary. Unknown telemetry or an unsupported shutdown path defaults to refusing automatic contribution until the owner selects a safe local policy. Attached-only endpoints may still be used with an explicit limitation, but cannot promise automatic reclamation.

| State | Local inference behavior | Exit condition |
| --- | --- | --- |
| Manual leech | No admissions; cancel and release managed inference | Explicit local owner action |
| Contributor idle or busy | Admit within current measured limits | User activity, manual withdrawal, maintenance, or failure |
| Withdrawing | Refuse admissions; cancel work and release resources | Release verified or fault identified |
| Automatic cooldown | No inference; routing and GUI remain available | Full quiet period plus safe health and resource checks |
| Resource fault | No unsafe new work; report the cause | Recovery and revalidation |

## Memory and execution admission

**MEMORY-01 — C.** Do not schedule beyond the node's configured RAM/VRAM safety margin. If two needed models will not fit together, wait for one request to finish and its model to unload before admitting the next load.

**MEMORY-02 — I.** Check actual free memory and reserve the expected peak before loading or starting work. Concurrent admissions on one host must not each allocate the same free capacity. Count loading, running, and retained caches; release a reservation only after cancellation or completion is settled and the resource state is known.

**MEMORY-03 — I.** Treat host RAM, each discrete GPU's VRAM, and unified memory appropriately. Do not add separate GPU memories as if any model could use the sum. Do not count Apple unified memory twice as independent RAM and VRAM. Respect the backend's actual sharding and device placement.

**MEMORY-04 — P, Q14.** Start with a local reserved margin of the greater of 15 percent or 2 GiB for host/unified memory, and the greater of 10 percent or 1 GiB per discrete GPU. Profiles may require larger margins. These are adjustable starting proposals, not a guarantee against provider allocation spikes or another program allocating memory concurrently.

**MEMORY-05 — I.** Resource admission includes measured execution concurrency and request size, not only whether weights fit. A provider with one proven slot gets one execution at a time. Provider internal queues must not hide Mango's ordering or continue running work Mango believes canceled.

**MEMORY-06 — I.** If an allocation fails, refresh observations, invalidate the unsafe profile, and stop retrying the same placement repeatedly. Surface a meaningful resource failure. A drop in free memory may require withdrawal even when the activity detector cannot identify its owner.

## Requests and queue ownership

**QUEUE-01 — C.** Accept simultaneous incoming requests from different nodes and clients. Each node tracks requests it receives. Work destined for another machine is submitted only to that serving node's queue, rather than duplicated across every peer.

**QUEUE-02 — I.** The ingress tracks the client connection, authentication, routing attempts, deadline, and terminal outcome. The serving node tracks admission, loading, execution, and its waiting queue. Use a network-unique request ID and an attempt ID so a transfer, retry, or log aggregation cannot count multiple attempts as separate client requests.

**QUEUE-03 — I.** Transfer requires an explicit accepted or rejected result. An ambiguous network failure must not cause another node to start the same request while the original may still be executing. Reserve one execution owner per attempt; use cancellation acknowledgment or expiry/fencing before safe reassignment. Do not promise general exactly-once execution across failures.

**QUEUE-04 — C.** If a lower-priority request cannot be served anywhere without displacing higher-priority work, reject it as overloaded rather than admitting it to a waiting queue. Same- or higher-priority requests may queue, subject to finite resource and queue limits.

**QUEUE-05 — C.** When a higher-priority request enters a queue, reject lower-priority queued requests back to their ingresses. Each ingress may reroute to another eligible destination; otherwise return overload. The scope of this purge is unresolved in Q16: the user's wording says all lower-priority requests in the node's queue.

**QUEUE-06 — P, Q16.** Apply priority rejection and eviction only to work competing for the same constrained resource set. Independent GPU or CPU capacity should continue serving lower-priority work if it does not delay or consume resources reserved for higher-priority work. This narrows the literal node-wide purge and requires approval.

**QUEUE-07 — P, Q18.** Ordinary higher-priority arrivals do not abort active requests. They reorder or displace waiting work. Active aborts are reserved for local resource protection, explicit cancellation, security revocation, failures, or a separately approved preemption policy. Idle loaded models may be unloaded; loading work that has not begun inference may be canceled safely when appropriate.

**QUEUE-08 — P, Q21/Q29.** Use bounded, initially memory-resident queues. Proposed starting limits: 64 waiting requests per serving node, 8 per key per node, and 120 seconds maximum queue residence for ordinary text/embedding work, with explicit task-specific limits for media. Apply bounded payload bytes as well as request counts. A crash fails affected requests; it does not silently resume old inference after restart.

**QUEUE-09 — I.** Cancel queued work promptly when its client disconnects, deadline expires, key is revoked, or it is displaced. Propagate cancellation to provider work already underway. A slow client must not hold unbounded generated output or an execution slot indefinitely.

**QUEUE-10 — P, Q21.** Return distinct machine-readable errors for invalid request, unauthorized, forbidden scope, unsupported operation, no compatible destination, rate limited, overloaded, deadline exceeded, local-resource withdrawal, and provider failure. Prefer HTTP 429 for a client's limit and 503 for unavailable network capacity, with a bounded retry hint where meaningful. Once streaming starts, use that protocol's stream error/termination semantics instead of pretending an HTTP status can be changed.

## Routing and priority order

**ROUTE-01 — C.** When an alias has multiple eligible deployments, use another endpoint for simultaneous independent work when that increases served requests. Avoid placing a small embedding job on the only large-model machine merely because the large machine is faster.

**ROUTE-02 — C.** Favor a request that has only one destination over a request that can fit on several, while honoring the overall goal of serving more requests, then priority, then FIFO. The statement that scarce-placement requests always take precedence conflicts with a strict reading of priority; Q17 records the recommended interpretation.

**ROUTE-03 — P, Q17.** Treat safety, authorization, and explicit priority admission rules as hard constraints. Within them, choose feasible placements that leave the most requests able to run; among contending requests of equal priority, prefer fewer eligible destinations, then FIFO. Scarcity does not promote a low-priority request over a high-priority request. This is a proposed reconciliation, not an assertion that the original wording already settled it.

**ROUTE-04 — I.** Eligibility includes the whole request: required protocol, features, modalities, context and output reserve, device safety, contribution state, and authorization. A model that fits its weights on another machine but cannot handle this request's context is not an alternate destination.

**ROUTE-05 — I.** Route from cached catalog and recent admission information. Contact likely destinations selectively with bounded attempts. The final serving node rechecks admission atomically. Do not poll all peers for every request or broadcast request bodies to candidate servers.

**ROUTE-06 — P, Q18/Q21.** Prevent load/unload thrashing by retaining useful loaded models until they obstruct better admissions, and by reserving an admitted scarce request's next feasible start. Stop backfilling conflicting work when it would postpone that reservation. Any backfill must fit without delaying it. Strict priority can starve low-priority work; do not secretly age it into a higher priority.

**ROUTE-07 — I.** Routing must terminate. Track attempted destinations and request deadlines, reject loops, use retry backoff, and retain FIFO age during a legitimate reroute without trusting client-supplied timestamps. FIFO is defined by admission order for equal contenders at the serving node, not a perfectly synchronized global arrival clock.

## Affinity and temporary request state

**AFFINITY-01 — C.** Remember routing decisions for subsequent related client requests. Waiting briefly for the endpoint with a useful cache may be better than moving to an idle endpoint that must process the entire prompt again.

**AFFINITY-02 — C.** Temporarily retain enough request information to distinguish continuation from an unrelated request by the same client. An unrelated request may use another deployment concurrently. One API key or source IP must not automatically pin all client traffic to one machine.

**AFFINITY-03 — P, Q19.** Prefer an explicit client session/conversation identifier scoped to authenticated key identity. Otherwise compare a bounded in-memory representation of relevant message prefixes and generation context, with a privacy-preserving digest where sufficient. Default to five minutes after the last completion and a bounded per-key and per-node footprint. Persist no prompt bodies solely for routing affinity. This five-minute default for ordinary routing is proposed; the five-minute future `best` requirement is confirmed.

**AFFINITY-04 — I.** Cache affinity is tied to the real provider instance, model/tokenizer/configuration, and usable cached prefix. The same alias does not make caches interchangeable. Invalidate hints after unloading, restart, relevant reconfiguration, or loss of state. An adapter that cannot confirm cache behavior may advertise only a best-effort preference.

**AFFINITY-05 — P, Q19.** Bound cache waiting by the client's deadline and an estimated cache benefit. Prefer waiting only when expected wait plus cached execution is better than the alternative. Make uncertainty visible in diagnostics; cache preference never overrides safety, scope, context fit, or the accepted queue priority rules.

## Relocation and failures

**MOVE-01 — C.** When a larger model needs a machine occupied by smaller models, finish appropriate active requests, unload the smaller models, and look up alternate hosts from saved catalog knowledge. If another host can serve them, tell their ingress to route future work there. Avoid a whole-network search for every displacement.

**MOVE-02 — I.** Internal route advice goes to the Mango ingress, not a mandatory HTTP redirect to the external client. The ingress preserves the client's URL, credentials, and stream. Advice is a hint that still requires current admission checks.

**MOVE-03 — I.** Moving a waiting request transfers its payload and ownership, not live KV cache. Moving future requests may lose cache benefit. Native backend conversation IDs or uploaded-file handles may prohibit movement until equivalent state is available.

**MOVE-04 — P, Q20.** Automatically retry only before output is committed to the client and when the operation is replay-safe. After partial text, audio, image progress, or provider-side effects, report interruption rather than silently restarting and concatenating results. Client-requested retries are new attempts with explicit semantics. Duplicate tool execution must not be hidden by a network retry.

**MOVE-05 — I.** After provider or peer loss, distinguish definitely rejected, definitely canceled, and outcome unknown. Propagate that distinction to the ingress. A node resuming from sleep must reconcile active attempt ownership before treating old work as current.

## Scheduling examples

| Situation | Required or proposed outcome |
| --- | --- |
| Two independent requests, alias available on two idle nodes | Run on both where safe; do not serialize merely because the key is the same. |
| Agent continuation on a busy instance with useful cache | Consider a bounded wait under AFFINITY-05; reroute if the benefit is absent or deadline is at risk. |
| High-priority small embedding request and scarce large-model request | Place embeddings on the smaller compatible machine; priority does not entitle it to the fastest GPU. |
| Low-priority request with no nonconflicting capacity behind high-priority work | Reject without queue admission. |
| High-priority request admitted behind active normal work | Under Q18's recommendation, let active work finish; displace lower-priority waiting competitors. |
| Normal request arrives while low-priority work waits | Evict affected low-priority queued work and attempt bounded rerouting. |
| Small models on the large machine; a large model is requested | Finish active work as permitted, reserve the large request, unload, and advise ingresses about alternatives. |
| Owner starts a game | Withdraw, abort managed inference, release resources, and enter the local cooldown. |
| Two ingresses simultaneously see one free slot | Only one admission succeeds; the other gets a queue decision or reroute/rejection. |
| Lower-priority work can use an independent GPU | Under Q16's recommendation, admit it if it cannot delay higher-priority reservations. |

# Mango interface and operations requirements

Every node provides a clear view of the network while keeping local resource protection under that machine's control. Logs and updates are network operations with explicit completion and failure states; an offline peer must never be reported as updated or cleared.

## GUI and settings ownership

**UI-01 — C.** Provide a responsive, intuitive GUI on each machine. From any node, an authorized user can inspect the network, configure provider/model listening and registration settings, change aliases, assign capabilities and ratings, and see the result across the network.

**UI-02 — C.** Activity monitoring, automatic withdrawal, cooldown, and RAM/VRAM safety margins can be changed only on the relevant machine. Remote access to shared model settings does not grant permission to disable another machine's protection.

**UI-03 — I.** Distinguish requested configuration, committed shared configuration, and effective host configuration. Show pending, applied, rejected, conflicted, and offline states. Do not display an optimistic save as completed when the owning node has not accepted it. Reconfiguring or disabling an endpoint must account for active work.

**UI-04 — I.** First-run setup supports creating a network or joining an existing one, Tailscale connection checks, credential recovery/export, contributor or leech selection, provider registration, lifecycle permission, and benchmark permission. If an existing network is temporarily unreachable, explain the failure rather than steering the user into accidental duplicate initialization.

**UI-05 — I.** The network view shows node identity and join order; contributor state and reason; reachability and metadata freshness; app/provider versions; models and aliases; effective context; resource limits; benchmark confidence; and loaded, running, queued, or unavailable status.

**UI-06 — I.** Request diagnostics explain the chosen destination, wait reason, effective priority, model loading, reroutes, rejection, and local withdrawal. Expose timing estimates as estimates. Live views must not force persistent request logging when logging is off.

**UI-07 — I.** Support keyboard navigation, screen-reader labels, readable contrast, scalable text, narrow windows, and non-color status indicators. Keep the UI usable while discovery, benchmarks, log collection, or updates run. Closing the GUI must not accidentally terminate background contribution unless the user selected that behavior.

**UI-08 — P, Q23.** Use a local desktop/tray experience with a background service and a browser-accessible local GUI for headless installations. Keep the administrative surface private and authenticated. Responsive does not automatically mean a native mobile application or internet-accessible admin page.

## Logging modes and request records

**LOG-01 — C.** Provide verbose, sparse, and off modes. Verbose records every request exactly. Sparse records request metadata without payload contents. Off does not persist request logs.

**LOG-02 — C.** Sparse metadata supports analysis by client/key name, model, destination, speed, elapsed wall time, request length, time to first token, model load delay, and queue delay. Key names are unique non-private labels chosen at creation and remain resolvable for historical reporting.

**LOG-03 — I.** Include stable request ID, attempt ID, ingress and serving node IDs, key ID and name-at-time, alias and actual deployment, task type, priority, start/end timestamps, outcome/reason, reroute count, and byte/token counts with units. Preserve the distinction between a client request and its multiple attempts so daily totals are not inflated.

**LOG-04 — I.** Timing records distinguish ingress receipt, admission, queue residence, provider load, prompt preparation, first output, completion, and response delivery where measurable. Use monotonic duration measurements on each host and wall-clock timestamps for ordering. Do not subtract unsynchronized clocks on different machines as though they shared one timer, and do not double-count overlapping load and queue intervals.

**LOG-05 — P, Q24.** Interpret the specification's `tts` metric as tokens per second for text; use the full name to distinguish it from text-to-speech. Preserve unknown or inapplicable values as such. Audio and image requests use relevant units such as input seconds, output seconds, pixels, or images, plus common latency measurements.

**LOG-06 — P, Q24.** Default to sparse logging. Verbose retains exact inference request bodies and relevant non-secret parameters, but excludes authorization headers, cookies, master/recovery material, provider tokens, and reusable credentials in known secret fields. This deliberately qualifies “exactly” at the credential boundary. Prompt content can itself contain secrets and remains sensitive. Response bodies are not retained by default.

**LOG-07 — I.** Log request content at one designated location, preferably ingress, and execution metadata at the serving node. Do not duplicate full payloads at every relay. Synthetic benchmark requests and future internal decision-model calls are identifiable so they do not masquerade as user traffic.

**LOG-08 — I.** Logging is bounded and must not block inference indefinitely. Show dropped, truncated, or failed records and disk exhaustion. A record missing bytes cannot be labeled an exact verbose capture. Temporary routing state is distinct from logging and must expire even when logging is off.

**LOG-09 — P, Q24.** With logging off, retain only state required to operate safely, such as configuration, credential revocations, deletion markers, and unfinished update status. Do not quietly retain a second per-request “security log.” A separate diagnostic export must be explicit and must describe its contents.

## Daily collection and retention

**LOG-10 — C.** At the end of each day, the surviving node with the lowest join ID requests logs from all other peers and builds a network-wide daily log. Support the same operation on demand. The collecting node may be a leech; collecting logs does not require inference contribution.

**LOG-11 — I.** “Surviving” means enrolled, not removed, and currently eligible/reachable under the agreed coordination policy, not merely present in an old catalog. A collector that disappears must not permanently prevent collection. The first node is not a permanent logging master.

**LOG-12 — P, Q05/Q25.** Select the lowest-join-ID reachable collector in the component authorized to coordinate. Use exclusive ownership of the collection job where available; make the aggregate idempotent and deduplicate if partitions or retries still produce multiple partial collections. An isolated component can keep a labeled partial view but cannot claim a complete network day.

**LOG-13 — P, Q25.** Use one configurable IANA timezone for network daily boundaries, defaulted from the first node during setup. Store timestamps in UTC. Daylight-saving days may be 23 or 25 hours. Do not independently interpret “end of day” in each peer's local timezone.

**LOG-14 — I.** Collect by node ID and event sequence/watermark in bounded chunks. Track nodes received, offline, logging off, failed, and beyond retention. Allow late arrivals to revise a daily aggregate without duplicating already collected events. Never report a missing peer as zero usage.

**LOG-15 — C.** Configure retention for the whole network, including how much log data any client preserves. Provide a network-wide clear action. Retention applies to raw records, daily aggregates, and attached verbose payloads rather than leaving hidden duplicate copies indefinitely.

**LOG-16 — P, Q25.** Start with seven days of local raw records and thirty days of aggregate metadata, subject to a 1 GiB total Mango log cap per node. Keep verbose payloads only for the raw retention window. Delete oldest data first and report when the byte cap shortens the intended time window. These defaults need approval.

**LOG-17 — I.** Network clear records a durable deletion generation, clears reachable local stores and aggregates, and marks unreachable peers pending. On reconnection, apply the deletion generation before accepting or uploading old logs. Clearing is not complete until all enrolled peers acknowledge or are explicitly removed. Data already exported by the user is outside Mango's control.

**LOG-18 — I.** Explain that a crashed or missing collector's local aggregate may be lost unless the original peer records still exist. Do not promise durable archival redundancy beyond the chosen retention and replication policy. Do not let log collection or verbose payload transfers monopolize inference traffic or interfere with local user activity.

## Software updates and compatibility

**UPDATE-01 — C.** When a node proposes an update, other nodes independently check the public release endpoint, determine whether their own host is eligible for that release, and queue eligible updates together. If compatibility cannot be verified for a peer, warn the initiating user against proceeding until the warning is manually overridden.

**UPDATE-02 — I.** Eligibility includes OS, architecture, Mango version, protocol range, configuration/data format migrations, required provider/API versions, runtime prerequisites, and available installation resources. A public version string alone is insufficient evidence of eligibility.

**UPDATE-03 — I.** Authenticate release metadata and artifacts against an established publisher trust root; verify integrity and protect against rollback or stale metadata. A peer's claim that a file is safe is not verification. A user override of mixed-version risk must not become an override of a bad artifact signature.

**UPDATE-04 — P, Q26.** Coordinate a common release intent and queueing window, then install in a controlled rolling order with local maintenance deferral and enough remaining capacity where possible. Simultaneous queueing does not require simultaneous restarts. Before restart, stop new admissions, drain work to a bounded deadline, and reroute waiting requests; do not silently abort active work to meet a synchronization timestamp.

**UPDATE-05 — C.** Different application versions do not automatically prevent connection. Warn and discourage avoidable divergence, but allow interoperable behavior where supported.

**UPDATE-06 — I.** Negotiate control and inference protocol features independently from application version numbers. A peer may remain connected for diagnostics while a specific unsupported operation is unavailable. Never accept an unsafe or undecodable message solely to avoid a version lockout.

**UPDATE-07 — P, Q27.** Publish a protocol compatibility matrix and support the current and immediately previous compatible protocol generation as a starting policy. Show exactly which operations cannot interoperate. A version label alone must not determine eligibility or feature support.

**UPDATE-08 — I.** Update states include proposed, verifying, eligible, incompatible, unreachable/unknown, queued, draining, installing, restarted, healthy, failed, and rolled back where supported. Offline nodes learn the desired release on reconnect and reverify before installing. They cannot be shown as already queued locally without acknowledgment.

**UPDATE-09 — P, Q26.** Back up Mango configuration before migration, use a recoverable install path, verify service health, and roll back only when the previous binary can safely read the preserved data. Treat an irreversible schema migration as a separate compatibility constraint, not something a binary swap automatically reverses.

**UPDATE-10 — P, Q26.** Coordinate Mango updates first. Do not automatically upgrade Tailscale, GPU drivers, provider applications, or model weights. Report dependencies that need local action. Avoid a peer instructing another peer to execute arbitrary downloads or commands.

**UPDATE-11 — I.** Automatic checks use bounded timeouts and backoff. Release verification failures, no eligible build, partial rollout, and a peer refusing or postponing an update remain visible. An update cannot disable local activity protection or rewrite local process permissions.

# Mango future best model routing

The `best` feature is explicitly deferred. Mango should record the information it will need, but should not yet run a decision model or choose unnamed models on the user's behalf. Serving a user-requested structured-decision endpoint is separate from using a decision model internally for routing.

## Future behavior

**BEST-01 — F.** A request for the reserved `best` model asks a configured decision model which capability is most relevant to the task, using the same user-defined labels that appear in model ratings. A programmatic selector then chooses an eligible deployment based on that capability and current availability.

**BEST-02 — F.** Before ranking, exclude deployments that do not satisfy the request's context, modality, technical feature, authorization, and local resource constraints. Include reserved output in context fit. A highly rated model that cannot accept the request is never a fallback candidate.

**BEST-03 — F.** First consider eligible deployments with open execution capacity for the identified task. Choose the best capability fit among those, rather than waiting for an unavailable model solely because its rating is higher.

**BEST-04 — F.** If none has open capacity, prefer eligible deployments whose models are already loaded, choosing the strongest capability among that group and applying normal queue rules. If that group cannot legally admit the request, queue for the best otherwise eligible deployment under normal admission rules. A low-priority request that cannot legally queue is still rejected as overloaded.

**BEST-05 — F.** Remember a short profile of the client and request. Prefer the same endpoint for related work until five minutes after the last completed request. A substantially different task can trigger a new decision. The preference remains subject to context fit, scope, safety, and current admission.

**BEST-06 — F.** Explain the selected capability, chosen alias/deployment, availability tier, and reason for a change in the GUI. Do not describe a user rating as an objective quality assessment.

## Proposed interpretation requiring Q28

**BEST-07 — P, Q28.** “Open capacity” may include an unloaded deployment that can safely load and start without waiting behind another request. The loaded fallback group means loaded but currently occupied deployments that can legally accept waiting work. Otherwise the stated fallback repeats the same empty group and does not define an executable selection rule.

**BEST-08 — P, Q28.** Use one primary capability label and per-deployment 0–5 ratings initially. Tie-break on feasible capacity, predicted completion delay, useful affinity, then a stable identifier. Do not introduce a composite learned score or unrequested optimization service before there is evidence it helps.

**BEST-09 — P, Q28.** The classifier must be an explicitly selected reachable decision deployment, never another `best` request. Give it a bounded prompt, output schema, latency budget, and compute budget. Treat its answer as data, not authorization or instructions to execute tools. Its work obeys resource protection and may not recursively invoke routing classification.

**BEST-10 — P, Q28.** Prefer an explicit client task label when supplied and allowed. If classification is unavailable or invalid, use an owner-selected fallback capability/model or return a clear routing error; do not invent a confident capability. Sending a prompt to a classifier is additional disclosure within the private network and must follow scope and logging policy.

## Information required before the feature exists

**BEST-11 — I.** The core catalog and request records should distinguish task labels and ratings, technical features, effective context, loaded state, admission hints, measured latency, client/session identity, and resolved deployment. This is useful to ordinary routing already and avoids a future ambiguity over what “best” means.

**BEST-12 — P, Q28.** Reserve `best` as a special name and return a clear feature-not-enabled result until the feature is implemented. Do not allow an ordinary alias to collide with it, and do not silently route it to a default model. Record the requested logical model separately from the resolved deployment.

## Future acceptance examples

| Scenario | Expected future result |
| --- | --- |
| Strong coding model is busy; a weaker eligible coding model has open capacity | Use the open model, subject to ordinary priority admission. |
| Highest-rated model cannot fit the context | Exclude it before ranking. |
| No open capacity; one eligible loaded model can queue legally | Prefer that loaded model according to the capability ranking. |
| No loaded model can admit; an unloaded eligible deployment can queue legally | Queue for the best eligible destination under normal scheduling. |
| No legal queue for this low-priority request | Return overload; `best` does not bypass rejection policy. |
| Related follow-up arrives four minutes after completion | Prefer the previous endpoint if still eligible and useful. |
| Follow-up arrives after five minutes or clearly changes task | Reevaluate without assuming the prior capability. |
| Decision model is unavailable | Apply the approved fallback or return a clear error, without recursive `best` calls. |

# Mango research and recommendations

The sources below are official project documentation, source documentation, and security guidance checked on November 11, 2026. They establish external constraints. Mango's proposed behavior and numerical defaults are engineering recommendations, not results measured by these sources. Provider support must eventually be qualified against specific released versions.

## PAIR and the product motivation

NVIDIA documents PAIR as routing independent requests between machines on the same local network. Its getting-started guide names Ollama, LM Studio, and llama.cpp, and explicitly says it does not pool GPU memory or split a request across systems. The guide also describes individual node updates. These facts support the comparison with Mango's WAN-first, extensible direction. They do not prove that PAIR has excessive idle resource use or that WAN operation is technically impossible. Those remain the user's experience and motivation, not a benchmark conclusion. [NVIDIA PAIR getting started](https://docs.nvidia.com/local-ai/nvpair/getting-started/)

**Recommendation:** make Mango's idle footprint and message rate measurable acceptance targets, and retain whole-request routing as the product boundary. Avoid making unmeasured superiority claims.

## Tailscale integration and public access

`tsnet` embeds Tailscale inside a Go application using a userspace network stack. It creates its own tailnet device identity and supports interactive authentication or authentication keys. Embedding can simplify packaging, but does not eliminate account sign-in, device approval, or network policy. [Tailscale tsnet](https://tailscale.com/docs/features/tsnet)

**Recommendation:** start with an installed Tailscale client, pending Q02. Evaluate embedding against the chosen application stack and measured total footprint later; do not select the whole stack merely because an embedding library exists.

Tailscale can use direct paths or relays when direct connectivity cannot be established. Relays may increase latency and reduce throughput, so routing cannot assume all tailnet peers behave like LAN hosts. [Tailscale connection types](https://tailscale.com/docs/reference/connection-types)

**Recommendation:** keep discovery and metadata compact, stream inference, use bounded timeouts, and account for actual request transfer costs. Text-only requests can still include long contexts; audio and image payloads can be much larger.

Funnel supplies public TLS access, with restrictions on tailnet domain names, listening ports, platforms, and bandwidth. It is a distinct public exposure mechanism, not a consequence of ordinary tailnet connectivity. [Tailscale Funnel](https://tailscale.com/docs/features/tailscale-funnel)

**Recommendation:** treat Funnel as an optional convenience, with a general HTTPS reverse-proxy path. Mango must authenticate inference independently and keep its administrative endpoints private. Q03 determines supported packaging.

Tailscale grants express access between sources and destinations at network and application levels. Mango still has to implement its own application permission semantics. [Tailscale grants](https://tailscale.com/docs/features/access-control/grants)

**Recommendation:** scope tailnet connectivity to Mango services instead of requiring unrelated host services to be reachable. A successful network connection is not sufficient Mango enrollment or inference-key authority.

The Tailscale local client API exposes an IPN notification watch. Its documentation marks that watch API as unstable, while identifying `WhoIs` as stable. [Tailscale local client API](https://pkg.go.dev/tailscale.com/client/local)

**Recommendation:** prefer events where supported, but qualify versions and retain a bounded fallback. Do not promise a portable, permanent discovery-event contract before checking the supported platform combinations.

| Unsloth | Its API guide documents chat, embeddings, image, audio, and structured decisions, conditional on version/backend/model. It also documents server-side tools and their bind-dependent defaults. [Unsloth API guide](https://unsloth.ai/docs/basics/api) | Integrate real serving profiles and probe operations. Explicitly disable host-executed tools when proxying remote inference into a localhost backend. |

**Recommendation:** retain separate provider, model artifact, alias, and loaded-instance records. Approve a concrete first-release protocol list in Q10. Do not claim every provider supports every modality merely because the Mango catalog can describe it.

## Activity monitoring and memory safety

NVIDIA's NVML process-memory documentation identifies a Windows WDDM case where per-process GPU memory is unavailable through that field. This is a concrete counterexample to assuming one vendor API can provide complete cross-platform attribution. [NVML process information](https://docs.nvidia.com/deploy/nvml-api/620/api/structnvmlProcessInfo__v1__t.html)

**Recommendation:** qualify native telemetry per OS/runtime/device, expose missing measurements, and default to conservative admission. Activity sampling is local work and can be necessary without violating the goal of avoiding repeated network polls. A benchmark is evidence of a workload's observed peak, not a guarantee that all larger workloads or overlapping models will fit.

## Credential and denial-of-service protection

OWASP recommends salted, slow, memory-hard password hashing and identifies Argon2id as a preferred option. That guidance concerns human passwords; Mango must distinguish their handling from high-entropy inference tokens. [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

**Recommendation:** use vetted identity and secret-storage components, separate password/recovery authority from runtime peer credentials, and review the enrollment design before coding. Do not design security around broadcasting a reusable master secret.

OWASP's API resource-consumption guidance calls for limits on payload size, execution work, memory, and request rates. Rate limits alone do not bound the cost of one oversized request or a lookup that fans out to many peers. [OWASP API resource consumption](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)

**Recommendation:** combine per-source limits with global bounds, concurrent-work limits, deadlines, and bounded caches. Never propagate an unknown-key query recursively. Limit valid credentials too: authentication does not establish a safe compute budget.

A disconnected node cannot learn a newly issued revocation until communication resumes. This is a constraint of the requested topology, not a provider defect. **Recommendation:** approve a bounded stale-authorization window and a fail-closed public policy in Q07. The proposed 60 seconds is a policy choice, not a guarantee available from push-only daily synchronization.

## Update verification

The Update Framework describes signed metadata, hashes, versions, expiration, and trust roles to resist compromised or stale update distribution. HTTPS transport alone does not supply those update guarantees. TUF concerns update discovery and verification; it does not itself implement Mango's installation rollback. [TUF overview](https://theupdateframework.io/docs/overview/)

**Recommendation:** use an established signed update system and separate compatibility override from authenticity verification. Queue a coordinated release but prefer rolling installation to avoid taking all serving capacity down together. Q26 and Q27 settle rollout and supported interoperability.

# Mango open decisions

This is the complete question set for the current requirements draft. Each recommendation is a proposed answer, not a decision already made. The other documents preserve confirmed requirements separately from these proposals.

You can answer by number, or say “Accept the recommendations except Q…” and list the changes. An accepted answer will update the requirements before the implementation plan is written. Technology choices and development stages are intentionally deferred.

## Product and connectivity

### Q01 Platforms and scale

Which platforms and operating envelope should the first qualified release promise?

**Recommended:** Windows, Apple-silicon macOS, and Linux for the Mango client and GUI, with provider/telemetry support qualified separately. Start with 1–20 nodes and 100 deployments. Use the proposed idle targets of under 1 percent of one CPU core, 150 MiB background-service memory, and 1 KiB/s average control traffic per node as targets to validate, not promises already established. Report the total footprint including Tailscale and the open GUI separately.

This makes “lightweight” testable without claiming unlimited scale. A narrower platform set would reduce initial qualification work. Affects PRODUCT-01, NFR-01–04.

### Q02 Tailscale installation

Should Mango require the existing Tailscale client or embed Tailscale?

**Recommended:** require an installed, authenticated client initially and make setup checks clear in the GUI. Retain embedding as a packaging option to assess after the stack is chosen. `tsnet` is real, but it creates another authenticated device identity and ties the direct embedding path to Go.

Embedding could improve first-run convenience, but its lifecycle, device permissions, and footprint need qualification. Neither option removes user authentication. Affects NET-03, PRODUCT-02.

### Q03 Public HTTPS

Which public exposure path should Mango support, and should it ever enable exposure automatically?

**Recommended:** exposure is off until the local owner enables it. Support a general HTTPS reverse proxy, with Tailscale Funnel as an optional guided path when its restrictions fit. Creating an inference key never enables public serving by itself. Publish only the inference surface.

A Funnel-only choice is simpler but imposes its domain, port, platform, and bandwidth constraints. Affects PUBLIC-01–04.

## Authority and consistency

### Q04 Administrative access from peers

Does joining the network grant unrestricted settings administration, or should sensitive changes require a fresh master-password unlock?

**Recommended:** all enrolled nodes may use resources and view shared state; any node may administer the network after a short local master unlock. Require it for key management, enrollment, shared configuration, retention clearing, and update policy. Keep resource protection and process-control permission local to the host regardless of unlock elsewhere.

This retains peer equality while limiting what an unattended unlocked GUI or ordinary peer credential can change. Public inference keys never become administrator credentials. Affects AUTH-07, UI setting boundaries.

### Q05 Shared changes during partitions

Should the network prioritize safe global ordering or accept administrative changes on isolated peers?

**Recommended:** serialize membership, ordered join IDs, authority changes, and shared configuration commits through a temporary coordinator with fenced authority and a majority of enrolled voting peers. Any node can originate the change. Inference and immediate local resource withdrawal continue without a majority. Model observations remain host-owned.

The cost is significant: in a two-node network, both must be online for globally committed writes. An alternative is eventual merging with explicit conflicts and weaker ordering guarantees. Do not hide this tradeoff behind “decentralized.” Affects NET-05, SYNC-03–05, LOG-12. Also determines whether Q06/Q07 can promise authoritative freshness.

### Q06 Password recovery and compromise

What should recovery preserve, and must the printed recovery record rebuild authority after all peer state is lost?

**Recommended:** support both password replacement on a surviving network and authority recovery from an adequate offline recovery record. Ordinary recovery rotates the master/recovery authority and invalidates administrative sessions while preserving enrolled nodes and existing inference keys. Offer a separate compromise-recovery action that revokes peers/keys and requires reenrollment. Neither path recovers deleted logs or provider secrets automatically.

A full compromise recovery is more disruptive but appropriate when secrets were stolen. Lost-all-peers recovery needs more than a short password-reset code and cannot reconstruct a lost catalog or key registry without a replica/backup. Forced recovery without the old quorum starts a new network generation and prevents old partitions from regaining write authority automatically. Affects AUTH-04–06.

### Q07 Revocation while peers are offline

How much stale authorization is acceptable, and what happens to work already using a revoked key?

**Recommended:** public ingress may accept only authoritative revocation state no older than 60 seconds, refreshed on demand during traffic; if freshness cannot be established, fail closed for new public work. Cancel queued and active requests as soon as their serving node learns the revocation, and refresh authority for long-running public work under the same bound. Trusted private peer inference may continue while partitioned, but known revocations always win.

This introduces bounded security-related network checks. Immediate worldwide revocation with indefinite offline availability is not achievable. A longer window improves availability but increases exposure. Affects KEY-07/09–11.

### Q08 Key policy and limits

Should keys have a fixed priority, what additional scopes should exist, and which initial limits are appropriate?

**Recommended:** one fixed low/normal/high priority per key, default normal; permitted task types plus optional alias restrictions; unique display name; 90-day default expiry with an explicit non-expiring choice for private integrations. Begin with the unknown-key lookup limits in KEY-07 and finite configurable per-key rate, concurrency, and payload limits. Label these limits as per-ingress unless a later network-wide quota design is explicitly required.

Trusted peer-originated work carries its node identity and defaults to normal priority; elevation requires administrative policy. Forwarding public traffic never removes its original restrictions. Do not promise a strict global rate quota from independent node counters. The exact workload-dependent valid-key limits can be tuned during qualification. Affects KEY-01–08, QUEUE-08.

## Providers and model contracts

### Q09 Authority over existing inference servers

May Mango shut down an existing server it did not start, and who grants that authority?

**Recommended:** the local owner explicitly places each provider in managed or attached mode. Managed mode grants a defined load/unload/stop path and is required for a promise of automatic resource reclamation. Attached mode permits inference but clearly states when Mango cannot release the provider's resources. Do not stop unrelated processes or the provider GUI merely because names match.

Automatic downloads, provider installation, training, and weight distribution remain outside the initial scope. This qualifies the original blanket shutdown behavior where Mango lacks control. Affects PROVIDER-03–07, RESOURCE-06/07, SCOPE-09.

### Q10 Initial API coverage

Which exact provider profiles and client protocols must the first complete release support?

**Recommended:** qualify Unsloth Studio/API and `unsloth run`, LM Studio native management plus inference, and supported llama-server single-model/router profiles. Cover model listing, chat completions with streaming and client-executed tool calls, embeddings, image generation, transcription, speech generation, and a specifically named structured-decision contract. Use the documented System One style as the decision-contract candidate to validate. Support each operation where the installed backend/model provides it.

Treat full Responses, Anthropic Messages, video, realtime duplex audio, and general persistent job/file workflows as separately approved extensions. This keeps image/audio/decisions in scope without promising every vendor API. Affects PROVIDER-07, API-01–04.

### Q11 Provider tools and code execution

May an inference request cause a provider to run code, browse, or invoke tools on a contributing host?

**Recommended:** no provider-side execution by default. Preserve tool calls returned to and executed by the client. Explicitly disable backend-hosted tools when forwarding into a localhost provider, because the backend may otherwise trust the request as local.

Allowing host execution would need separate local permission, key scope, isolation, and failure semantics. It should not be smuggled into ordinary text inference. Affects API-05.

### Q12 Alias compatibility beyond modalities

Should alias validation remain strictly modality-only, or add technical checks for outputs that must be interchangeable?

**Recommended:** retain exact matching of input/output modality sets and never validate quality claims. Also require compatible embedding dimensions/encoding and warn that equal dimensions do not establish a common vector space. Pin an embedding collection to a deployment or owner-declared compatible family. Preserve deployment-specific feature and context checks for every request.

The embedding rule is an explicit extension to your validation limit; it prevents silent corruption without judging model intelligence. If rejected, record that callers assume all embedding compatibility risk. Affects MODEL-02–06.

### Q13 Benchmark permission and context verification

Should full-context tests run automatically even when expensive, and how should unreported limits be handled?

**Recommended:** get local permission for the benchmark suite, show its expected size, and make it cancelable. Measure short, half, and full usable context with reserved output and synthetic input, subject to a time/resource budget. Mark skipped or failed tests incomplete and schedule conservatively. Require a configured or verified served limit when the provider cannot report one; never silently substitute the model's theoretical maximum.

This retains your full-context measurement requirement while allowing an enormous or unsafe test to be deferred honestly. Affects CONTEXT-04, BENCH-01–06.

### Q14 Memory safety defaults

Which default safety margins and overlap policy should apply before a node is fully characterized?

**Recommended:** reserve the greater of 15 percent or 2 GiB host/unified memory and the greater of 10 percent or 1 GiB per discrete GPU, adjustable locally. Use conservative non-overlap for unmeasured combinations. Require context/concurrency peak evidence and a live admission check before overlapping models.

These are starting values to calibrate, not universal guarantees. A provider can still allocate unexpectedly, and another local program can race for memory. Affects MEMORY-01–06, BENCH-06.

### Q15 Activity detection and cooldown

What should trigger withdrawal, when should contribution resume, and what happens when process attribution is unavailable?

**Recommended:** local CPU/GPU/memory observation with up to 2-second samples, a 10-second sustained external-load trigger, immediate withdrawal for severe memory pressure, and five continuous quiet minutes before resuming. Renew the quiet period on new load. Manual leech mode persists. Treat missing attribution as a visible limitation and require a conservative local choice before automatic contribution.

The provisional external-load threshold needs hardware calibration; detecting “any input” should not automatically mean heavy load. Affects RESOURCE-02–07.

## Scheduling and client behavior

### Q16 Scope of queue purging

Should a higher-priority arrival clear every lower-priority queued request on that node, or only requests competing for the same resources?

**Recommended:** clear only conflicting lower-priority work. A job using an independent GPU or genuinely nonconflicting CPU capacity should continue or be admitted if it cannot delay the higher-priority reservation.

This is a deliberate narrowing of “all lower priority requests in the queue.” Literal node-wide purging is simpler to describe but can reject useful work without freeing the needed resource. Affects QUEUE-05/06.

### Q17 Scarcity versus priority

Does a low-priority request with one possible destination outrank a high-priority request with several destinations?

**Recommended:** no. Keep safety, authorization, and the explicit priority admission/rejection rules hard. Route flexible work elsewhere to maximize service, then use fewer eligible destinations to break contention among equal-priority requests, followed by FIFO.

Your “always lower priority” scarcity sentence and the later priority hierarchy conflict in this case. If scarcity should override key priority, say so explicitly; the queue rejection rules will need corresponding changes. Affects PRODUCT-05, ROUTE-02/03.

### Q18 Active work and starvation

Should ordinary priority changes abort running inference, and how should a waiting large model avoid endless postponement by small requests?

**Recommended:** let active requests finish during ordinary scheduling. Higher priority displaces queued work, while local activity, explicit cancellation, revocation, and faults can abort active work. Reserve an admitted scarce request's next feasible start and stop backfilling jobs that would delay it. Permit safe cancellation of loading work before inference begins when justified.

Retain strict priority rather than silently aging low-priority work upward; under sustained high load, low-priority work may starve or be rejected. Affects QUEUE-07, ROUTE-06, MOVE-01.

### Q19 Client identity and affinity

How should Mango identify a continuing conversation, how long should it remember it, and how long may cache reuse delay a request?

**Recommended:** use an explicit session identifier scoped to authenticated key identity, with bounded in-memory prefix comparison/digests as fallback. Expire ordinary affinity five minutes after completion. Keep unrelated work under the same key independent. Wait for a cached instance only when estimated benefit beats another placement and the client deadline permits it.

Never equate source IP or API key with one conversation. Do not persist prompt bodies solely for affinity. Affects AFFINITY-01–05; the future `best` five-minute rule is already confirmed.

### Q20 Retries and partial results

May Mango automatically restart a request elsewhere after execution starts or the client has received output?

**Recommended:** automatic retry only when no output has been committed and the operation is known to be replay-safe. After partial output or possible side effects, return an interruption with request/attempt identity. Require an explicit client retry rather than concatenating a second generation into the original stream.

Reassigning queued work remains allowed after ownership transfer. Live cache or backend-held conversation migration is not promised. Affects QUEUE-03, MOVE-03–05.

### Q21 Queue limits and overload

What bounds and failure contract should apply when work cannot start promptly?

**Recommended:** start with 64 waiting requests per serving node, 8 per key per node, and 120 seconds of queue residence for ordinary text/embedding work, plus finite byte limits and separate media deadlines. Use 429 for a client's rate/quota limit and 503 for unavailable inference capacity, with clear reason codes and useful retry hints. Bound rerouting attempts by distinct candidates and the request deadline.

Long-running media may need larger explicit deadlines; no request should wait indefinitely. These counts are tuning defaults, not a substitute for byte/resource limits. Affects QUEUE-08–10, ROUTE-07.

### Q22 Low traffic and failure detection

Is a small amount of bounded liveness and local inventory checking acceptable when event APIs are insufficient?

**Recommended:** yes. Prefer events, cached state, demand-driven checks, and daily reconciliation. Allow a slow local provider fallback, initially no more often than once a minute while enabled, and cheap bounded checks for active routing, security freshness, and temporary coordination. Do not scan every peer per request or fetch unchanged full catalogs repeatedly.

Without these exceptions, an externally changed server or dead peer can remain stale until the next request or daily refresh. Event API support also differs by provider/version. Affects SYNC-06, NFR-03, NET-03, KEY-09.

## Interface and operations

### Q23 GUI form and headless machines

Should the product support headless machines, and what form should the GUI take?

**Recommended:** a desktop/tray experience backed by a service, with an authenticated local browser GUI usable for headless deployments. Keep the layout responsive and accessible, and allow shared model administration from any enrolled node. Resource-protection settings still require local host access.

Do not add a native mobile app or publicly exposed admin console to the initial scope. The exact UI technology belongs in the later plan. Affects UI-01–08.

### Q24 Logging contents and privacy

Should sparse logging be the default, what does verbose “exactly” include, and does `tts` mean tokens per second?

**Recommended:** default sparse; interpret `tts` as tokens per second and name it explicitly. Verbose records exact inference request bodies with explicit credential exclusions; do not retain response bodies by default. Off creates no persistent request logs, including a hidden per-request audit trail. Required revocation/configuration/update state remains operational state, not logging.

If full responses are wanted, add them explicitly with retention and storage implications. Prompt text can contain secrets even after transport credentials are removed. Affects LOG-01–09.

### Q25 Daily logs and deletion

Which day boundary, retention, completeness, and clearing behavior should apply across intermittently connected nodes?

**Recommended:** one network timezone selected at setup, defaulting to the first node's timezone; UTC timestamps; seven days of raw records and thirty days of aggregate metadata, within a 1 GiB per-node total cap. The lowest eligible join ID collects; offline peers produce a visibly incomplete aggregate, with late merge and deduplication. Network clear remains pending for offline peers and applies a deletion generation before their old data can rejoin.

This does not guarantee archival redundancy or deletion of user exports. Affects LOG-10–18.

### Q26 Coordinated updates

Does “at the same time” mean coordinated queueing or simultaneous restart, and how much can a node update automatically?

**Recommended:** coordinate one verified release intent and queueing window, then perform rolling installation with bounded draining, local deferral, health verification, and rollback when the data format permits it. Warn before proceeding when a peer cannot verify eligibility; require the initiating user's explicit compatibility-risk override. Never override an invalid signature.

Coordinate Mango only. Leave Tailscale, drivers, providers, and model weights under their own update controls. Simultaneous restarts would deliberately remove all capacity and complicate recovery. Affects UPDATE-01–04/08–11.

### Q27 Mixed-version compatibility

How much backward compatibility should releases promise without requiring all nodes to match?

**Recommended:** publish a feature/protocol compatibility matrix and initially support the current and previous compatible protocol generation. Negotiate shared features regardless of application version numbers. Keep diagnostic connectivity where possible, but reject specifically incompatible operations safely.

“Do not lock out different versions automatically” cannot mean decoding unknown or unsafe protocols. Affects UPDATE-05–07.

## Deferred best routing

### Q28 Best-model interpretation and preparation

Are the proposed capability ratings, capacity tiers, classifier fallback, and reserved name appropriate for the future feature?

**Recommended:** shared labels and deployment-specific 0–5 ratings with unrated distinct from zero; one primary task label; first choose the strongest eligible open-capacity deployment, including safe immediate cold loading; then prefer eligible loaded deployments that can legally queue; then the best other legal queue. Keep five-minute related-request affinity. Use one explicitly configured decision deployment, bounded classification, and an owner-chosen fallback or clear error if it is unavailable. Reserve `best` now, but do not run this feature yet.

This resolves the otherwise ambiguous loaded-but-no-capacity fallback and keeps classification from becoming recursive. It does not judge user model ratings. Affects MODEL-05, BEST-01–12.

## Request recovery

### Q29 Queue survival after crashes

Should queued inference survive a Mango restart and execute later automatically?

**Recommended:** no durable inference queue initially. Keep bounded queues in memory, fail outstanding client connections clearly on restart, and require client retry under the replay policy. Persist configuration and required security/update state, not a hidden backlog of prompts.

Durable media jobs may later require a separate explicit contract with result retrieval, cancellation, retention, and duplicate-execution protection. Affects QUEUE-08, API-04, MOVE-05.

Mango combines independently hosted inference services into one private network.
